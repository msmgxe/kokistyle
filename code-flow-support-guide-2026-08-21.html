Flujo transversal 01

Autenticación, cookie de sesión y JWT para RLS

Este es el flujo que cualquier soporte debe conocer primero: una vista puede cargar, pero una operación de datos fallará si no existe la cookie o si el JWT no tiene los claims esperados.

Entrada por PIN o dispositivo

El PIN ya debe canjearse por una cookie firmada

La sesión de servidor evita que una ruta API confíe en role o permisos enviados desde el navegador. El PIN sólo sirve para abrir la sesión.

1Usuario abre modalAdminModal / AuthContext.login() recibe PIN; shortcut usa token de dispositivo.
2Login server-side/api/auth/login limita IP y comprueba PIN con checkPin().
3Verifica / migra PINlib/pin.ts usa scrypt. Si detecta PIN legacy válido, lo hashea y borra el claro.
4Emite cookie HttpOnlylib/session.ts firma HMAC-SHA256 y entrega lux_session, SameSite=Lax.
5Solicita token Supabasesupabase.ts pide /api/auth/supabase-token y lo conserva sólo en memoria.
6RLS decide por filaJWT authenticated lleva lux_role y lux_projects; las policies autorizan la consulta.
Archivos clave
  • context/AuthContext.tsx
  • lib/session.ts
  • lib/pin.ts
  • lib/supabase-jwt.ts
  • api/auth/{login,session,supabase-token}
Bibliotecas
  • React Context
  • node:crypto (HMAC + scrypt)
  • @supabase/supabase-js
  • Next cookies / route handlers
Diagnóstico
  • Network: login debe devolver Set-Cookie.
  • /api/auth/supabase-token debe devolver token + expiry.
  • Un 401 API = cookie ausente/expirada.
  • Un resultado vacío/403 de Supabase = revisar RLS y claims.
Transición importante: si no está configurado SUPABASE_JWT_SECRET, supabase-token devuelve null y el cliente usa la anon key como fallback. No considerar completa la fase RLS hasta aplicar las migraciones y comprobar que el navegador recibe un JWT.
Flujos 02–03

Dashboard, alta y detalle de proyecto

Dashboard: vista consolidada de la operación

El dashboard no usa una API de agregado: lee datos operativos con Supabase y calcula KPI/totales en el cliente.

Usuario abre /proyectos
1/proyectosEl layout valida isAdmin y monta proveedores de voz, tema e idioma.
2DashboardPageproyectos/page.tsx carga proyectos y dispara enrichWithEstimateBudgets().
3Consultas Supabaseprojects + payments, expenses, tasks; estimates/secciones/items se consultan explícitamente.
4Calcula en UIutils.ts y estimateTotals.ts generan avance, balance, KPIs y presupuesto efectivo.
5Cards + modalProjectCard, ProjectFormModal y ReportBuilder muestran o mutan datos.
Datosprojects, payments, expenses, tasks, project_estimates, estimate_sections/items.
LibreríasReact, next/link, lucide-react, @supabase/supabase-js.
Cuando fallaCompruebe primero el query que queda vacío. Luego compruebe lux_projects y policy de esa tabla; por último revise el cálculo local.

Detalle: el contenedor de casi todas las operaciones de obra

src/app/proyectos/[id]/page.tsx es el orquestador. Descarga el proyecto y pasa partes a tabs locales para no cambiar de ruta por cada operación.

1Card / URL con idUsuario abre /proyectos/[id]; useParams() entrega el identificador.
2fetchProject()La página carga cabecera y colecciones relacionadas; también carga contactos y contexto de voz.
3Proyecto + hijostasks, materials, payments, expenses, notes, contacts, fotos y objetivos se hidratan en estado React.
4Tab especializadoEstimateTab, DayPlannerModal, ProjectPhotos, DesignTab o tab interno recibe props y callbacks.
5Mutación + refreshEl tab escribe en Supabase; callback/estado refresca la vista y toast confirma.
Soporte: si un tab no muestra datos pero el proyecto abre, compare el project_id de su query contra el id de URL. Si la edición se ve y desaparece al recargar, la mutación no llegó a Supabase o RLS la rechazó.

Planner, Gantt, materiales, caja, fotos y equipo

Planner y Gantt: actividades derivadas o manuales

El Planner no duplica el Estimate: usa estimate_item_id/source_key para saber si una tarea nace de un ítem del estimado. Gantt consulta las tareas ya calendarizadas.

1Tab Planner / PlanEn detalle de proyecto o vista global /proyectos/plan.
2DayPlannerModalConstruye pool desde Estimate y tareas existentes; usuario arrastra cards con dnd-kit.
3TasksINSERT para nuevas; UPDATE scheduled_date, estado, duración, contacto y source_key para existentes.
4GanttCalendarConvierte fecha/duración/estado en escala y barras; GanttCalendar.tsx es visual, no la fuente de verdad.
5Reporte / PDFPlan y DailyReport filtran tareas y generan sus reportes con pdf.ts.

Materiales y Cash Flow: el checkbox también puede crear un gasto

La compra de un material tiene una integración intencional: marcar “comprado” genera gasto y desmarcarlo elimina/revierte el gasto asociado.

1Materials / Cash FlowTabs del detalle; editar, comprar o registrar pago/egreso manual.
2MaterialesTab / PagosTabValida campos, conserva estado local y abre editor/confirmación.
3materialsNombre, proveedor, costo, cantidad y bought; opcionalmente enlazado a Estimate.
4expenses / paymentsCompra inserta expense con material_id; cobros y egresos alimentan balance.
5KPI y reportesutils.ts calcula ingresos, gasto y cash flow; dashboard los agrega por proyecto.
Soporte: un doble gasto suele significar que se marcó compra dos veces sin respetar el vínculo expenses.material_id. Verifique primero el expense asociado antes de tocar el total.

Un archivo no basta: se sube al bucket y la URL/ruta se guarda en una tabla o JSONB. Borrar una foto debe contemplar ambos lados.

4Metadatosproject_photos guarda URL, tag, álbum y orden; notas guardan adjuntos JSONB.

Flujos 10–11

Katy, transcripción y AI Design

Katy: voz → texto → intención → confirmación → escritura

La IA interpreta, pero el navegador conserva la decisión final sobre mutaciones. Las lecturas de datos se ejecutan en el servidor de voz; las acciones de escritura regresan como una tarjeta para confirmar.

1VoiceFABSpeechRecognition si existe; si no, MediaRecorder graba audio.
2Transcribe fallback/api/voice/transcribe valida sesión/rate-limit y llama Whisper en Replicate.
3Contexto de pantallaEl FAB envía historial, idioma, proyecto en foco y permisos de UI a /api/voice.
4Voice routeResuelve sesión, aplica rate limit y define herramientas de consulta/escritura.
5Claude HaikuAI SDK usa tool calling: responde texto o una intención estructurada.
6Tarjeta editableSi es escritura, usuario corrige y pulsa Confirmar; si es lectura, recibe respuesta hablada/texto.
7Supabase + auditoríaLa confirmación inserta/actualiza tabla del dominio y registra voice_actions.
ArchivosVoiceFAB.tsx, api/voice/route.ts, api/voice/transcribe/route.ts.
Librerías / APIsAI SDK, Anthropic, Replicate, Web Speech API, MediaRecorder, AudioContext.
DiagnósticoSin micrófono: permisos navegador. Sin texto: transcribe/Replicate. Respuesta errónea: payload/contexto + tool call. No guarda: tarjeta confirmada, sesión o RLS.

AI Design: prospecto público o uso interno

El flujo público usa un prospectId y límite de renders; el interno usa la sesión de superadmin. Gemini es preferido y Replicate es fallback.

1Landing AI Preview / DesignTabUsuario proporciona foto, habitación, estilo y objetivo.
2Sube fotoCliente la guarda en kokistyle-files y recibe URL/ruta.
3Render o Scope/api/design-render verifica sesión/prospecto y rate limit; design-scope analiza la foto.
4Modelo de imagenGemini Flash Image primero; si falla, Replicate interior-design. Scope usa Anthropic.
5PersistenciaRender se sube a Storage; prospecto incrementa renders_used; scope puede insertar Estimate sections.
6ResultadoAntes/después o secciones propuestas; usuario puede llevarlas al Estimate.
Soporte: “limit reached” se explica por FREE_RENDER_LIMIT y prospects.renders_used. Imagen no disponible: verificar URL fuente, Storage y credencial Gemini/Replicate. Mantener allowlist/validación de URL para evitar que el servidor descargue destinos internos.

Procedimiento universal

Cómo atender un ticket sin adivinar

Siga la secuencia. Cada paso reduce el área de búsqueda y deja evidencia antes de pasar al siguiente nivel.

1

Reproducir

Registre URL, proyecto, usuario/rol, dispositivo, acción exacta y hora. Nunca solicite PIN ni token en un ticket.

2

Network

Identifique la primera request roja. Guarde status y response: 401 sesión, 403 RLS, 429 límite, 5xx servidor/proveedor.

3

Frontera

Decida si el fallo está en componente, API route, query Supabase/Storage o proveedor. Use el color del diagrama.

4

Datos y policy

Valide project_id, estado de la fila y policy RLS con el rol real. No “arregle” permisos de UI para ocultar un 403.

5

Confirmar

Pruebe con rol permitido y no permitido, recargue y verifique que la mutación persistió. Documente causa, no sólo solución.

Atajos de diagnóstico por código HTTP

  • 401: falta cookie lux_session, venció o endpoint requiere sesión.
  • 403: sesión válida sin claim/proyecto permitido, o policy RLS bloquea.
  • 429: limitByIp() activó ventana de la ruta; espere Retry-After.
  • 400: payload/formato inválido; lea respuesta de la route.
  • 502/5xx: SMTP, Anthropic, Gemini, Replicate, Storage o error de servidor; abrir logs Vercel.

Deuda técnica que debe seguir visible

  • El rate limit actual es en memoria por instancia serverless: no es una cuota global dura.
  • Eliminar fallback de credenciales en body (adminPin/adminToken) cuando todas las sesiones antiguas hayan migrado.
  • Completar policies RLS y bucket privado antes de confiar en el fallback JWT/anon.
  • Separar gradualmente queries de componentes en repositorios/BFF y añadir pruebas de roles/RLS.
